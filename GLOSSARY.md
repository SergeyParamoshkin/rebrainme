# 📖 Глоссарий терминов - Rate Limiting и Retry паттерны

## 🔤 Основные термины

### **Rate Limiting**
**Определение:** Механизм ограничения количества запросов, которые клиент может отправить за определённый период времени.

**Зачем нужен:**
- Защита от DDoS атак
- Предотвращение перегрузки сервера
- Справедливое распределение ресурсов
- Соблюдение SLA

**Пример:** API GitHub позволяет делать максимум 5000 запросов в час для авторизованных пользователей.

---

### **Token Bucket Algorithm**
**Определение:** Алгоритм ограничения скорости, где токены добавляются в "корзину" с постоянной скоростью, и каждый запрос потребляет один токен.

**Как работает:**
1. Корзина имеет максимальную ёмкость (capacity)
2. Токены добавляются с фиксированной скоростью (rate)
3. Запрос обрабатывается, если есть доступный токен
4. Позволяет обрабатывать всплески трафика

**Формула:** `tokens = min(capacity, tokens + elapsed_time * rate)`

---

### **Sliding Window Log**
**Определение:** Алгоритм, который хранит временные метки всех запросов в скользящем временном окне и подсчитывает их количество.

**Преимущества:**
- Точный подсчёт запросов
- Плавное скольжение окна

**Недостатки:**
- Требует больше памяти для хранения временных меток

---

### **Leaky Bucket Algorithm**
**Определение:** Алгоритм, где запросы помещаются в очередь (ведро) и обрабатываются с постоянной скоростью, как вода, вытекающая из дырявого ведра.

**Особенности:**
- Сглаживает всплески трафика
- Обеспечивает постоянную скорость обработки
- Может вызывать задержки при всплесках

---

### **Retry**
**Определение:** Механизм повторной отправки запроса после неудачной попытки.

**Когда использовать:**
- Временные сетевые ошибки
- Перегрузка сервиса (503 Service Unavailable)
- Таймауты соединения

**Когда НЕ использовать:**
- Ошибки валидации (400 Bad Request)
- Ошибки авторизации (401, 403)
- Ресурс не найден (404)

---

### **Exponential Backoff**
**Определение:** Стратегия retry, где время ожидания между попытками увеличивается экспоненциально.

**Формула:** `delay = min(initial_delay * (multiplier ^ attempt), max_delay)`

**Пример:**
- 1-я попытка: подождать 100ms
- 2-я попытка: подождать 200ms
- 3-я попытка: подождать 400ms
- 4-я попытка: подождать 800ms

---

### **Jitter**
**Определение:** Добавление случайной задержки к времени ожидания для предотвращения синхронизации повторных попыток от множества клиентов.

**Формула:** `delay_with_jitter = delay + random(-jitter_range, +jitter_range)`

**Зачем нужен:** Предотвращает "thundering herd problem"

---

### **Thundering Herd Problem**
**Определение:** Проблема, возникающая когда большое количество процессов или потоков одновременно "просыпаются" и пытаются получить доступ к одному ресурсу.

**Примеры:**
- Все клиенты повторяют запросы через одинаковые интервалы после сбоя
- Кэш истекает, и все клиенты одновременно идут в БД
- Все воркеры просыпаются по одному событию

**Решение:** Jitter, случайные задержки, распределённые таймауты

---

### **Circuit Breaker Pattern**
**Определение:** Паттерн, который предотвращает попытки выполнить операцию, которая, вероятно, завершится неудачей.

**Состояния:**
- **Closed (Закрыт):** Нормальная работа, запросы проходят
- **Open (Открыт):** Запросы блокируются немедленно
- **Half-Open (Полуоткрыт):** Пробный запрос для проверки восстановления

**Переходы:**
```
Closed --(failures > threshold)--> Open
Open --(timeout elapsed)--> Half-Open
Half-Open --(success)--> Closed
Half-Open --(failure)--> Open
```

---

### **Retry Budget**
**Определение:** Механизм ограничения количества retry попыток на основе процента успешных запросов.

**Как работает:**
- Отслеживает процент успешных запросов
- Разрешает retry только если успешность выше порога
- Защищает downstream сервисы от перегрузки

**Пример:** "Разрешить retry только если успешность > 50% за последние 10 секунд"

---

### **Context (в Go)**
**Определение:** Механизм для передачи deadlines, сигналов отмены и других значений между горутинами.

**Основные функции:**
- `WithTimeout`: Автоматическая отмена после таймаута
- `WithDeadline`: Отмена в конкретное время
- `WithCancel`: Ручная отмена
- `WithValue`: Передача метаданных

**Пример использования:**
```go
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()
```

---

### **HTTP Status Codes (важные для темы)**

#### **429 Too Many Requests**
**Определение:** Клиент отправил слишком много запросов за определённый период времени.

**Заголовки ответа:**
- `Retry-After`: Время в секундах до следующей попытки
- `X-RateLimit-Limit`: Максимум запросов
- `X-RateLimit-Remaining`: Осталось запросов
- `X-RateLimit-Reset`: Время сброса лимита

#### **503 Service Unavailable**
**Определение:** Сервер временно не может обработать запрос из-за перегрузки или технического обслуживания.

**Когда используется:**
- Перегрузка сервера
- Плановое обслуживание
- Временные проблемы с зависимостями

---

### **Idempotency**
**Определение:** Свойство операции, которая при многократном применении даёт тот же результат, что и при однократном.

**Важно для retry:** Только идемпотентные операции безопасно повторять.

**Идемпотентные HTTP методы:**
- GET, HEAD, OPTIONS (безопасные)
- PUT, DELETE (идемпотентные)

**НЕ идемпотентные:**
- POST (обычно)

---

### **Backpressure**
**Определение:** Механизм, при котором downstream компонент сигнализирует upstream компоненту о необходимости снизить скорость отправки данных.

**Реализация:**
- Rate limiting
- Буферизация с ограничением
- Отклонение запросов (load shedding)

---

### **Load Shedding**
**Определение:** Преднамеренное отклонение части входящих запросов для предотвращения полного отказа системы.

**Стратегии:**
- Отклонение случайных запросов
- Приоритизация важных запросов
- Отклонение самых старых запросов в очереди

---

### **Bulkhead Pattern**
**Определение:** Паттерн изоляции ресурсов, где сбой в одной части системы не влияет на другие части (по аналогии с переборками в корабле).

**Реализация:**
- Отдельные пулы потоков для разных операций
- Изоляция критических путей
- Разделение ресурсов по приоритетам

---

### **Timeout**
**Определение:** Максимальное время ожидания ответа от операции перед её принудительным завершением.

**Типы:**
- **Connection timeout:** Время установления соединения
- **Read timeout:** Время ожидания данных
- **Total timeout:** Общее время операции

---

### **Deadline**
**Определение:** Абсолютное время, после которого операция должна быть отменена.

**Отличие от timeout:**
- Timeout: "подожди 5 секунд"
- Deadline: "закончи до 15:30:00"

---

### **Graceful Degradation**
**Определение:** Способность системы продолжать функционировать с уменьшенной функциональностью при сбое некоторых компонентов.

**Примеры:**
- Возврат кэшированных данных при недоступности БД
- Отключение рекомендаций при сбое ML-сервиса
- Упрощённый интерфейс при высокой нагрузке

---

### **SLA (Service Level Agreement)**
**Определение:** Соглашение об уровне обслуживания между поставщиком и потребителем сервиса.

**Метрики:**
- **Availability:** 99.9% uptime (43.2 минуты downtime в месяц)
- **Latency:** 95% запросов < 200ms
- **Error rate:** < 0.1% ошибок

---

### **Metrics & Monitoring**

#### **Counter**
**Определение:** Метрика, которая только увеличивается (количество запросов, ошибок).

#### **Gauge**
**Определение:** Метрика, которая может увеличиваться и уменьшаться (текущее количество соединений, использование памяти).

#### **Histogram**
**Определение:** Метрика для измерения распределения значений (время ответа, размер запроса).

#### **Summary**
**Определение:** Похож на Histogram, но вычисляет квантили на клиенте.

---

### **Distributed Tracing**
**Определение:** Метод отслеживания запросов через несколько сервисов в распределённой системе.

**Компоненты:**
- **Trace:** Полный путь запроса
- **Span:** Единица работы в trace
- **Context propagation:** Передача trace ID между сервисами

---

## 🔗 Связанные концепции

### **CAP Theorem**
- **Consistency:** Все узлы видят одинаковые данные
- **Availability:** Система остаётся доступной
- **Partition tolerance:** Система продолжает работать при сетевых разделениях

### **Eventual Consistency**
**Определение:** Модель согласованности, где система гарантирует, что все узлы придут к согласованному состоянию, но не сразу.

### **Strong Consistency**
**Определение:** Модель, где все узлы всегда видят одинаковое состояние данных.

## 🎯 Практические советы

1. **Всегда используйте jitter с exponential backoff**
2. **Мониторьте retry budget - это ранний индикатор проблем**
3. **Circuit breaker должен иметь алерты при открытии**
4. **Rate limiting должен возвращать заголовки с информацией о лимитах**
5. **Используйте идемпотентные операции где возможно**
6. **Документируйте SLA и придерживайтесь их**
7. **Тестируйте поведение при сбоях (chaos engineering)**
